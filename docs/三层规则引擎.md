# NginxGuard 三层规则引擎

本文档描述当前仓库中 `engine.lua`、`access.lua` 与 `lib.lua` 的实际实现。三层分别是基础检测器（L1）、组合规则（L2）和动作执行（L3）。组合规则文件为 `rule-config/combo.jsonl`。

## 1. 请求处理顺序

Nginx 在 access 阶段执行 `access.lua`。文件加载时注册检测器，随后每个请求按以下顺序处理：

```text
Nginx access 阶段
  └─ waf_main
      ├─ Nginx/WAF 开关关闭 → 返回
      ├─ IP 白名单命中 → 返回（不进入组合规则）
      ├─ L2 读取并评估 combo.jsonl
      │   ├─ 按文件顺序执行规则表达式
      │   ├─ 表达式叶子按需调用 L1 检测器，命中事实缓存到 ngx.ctx
      │   └─ 命中规则时执行 L3 动作；终止请求的动作立即返回
      └─ 传统检测流程（复用 L1 结果缓存）
          ├─ dynamic_black_ip → black_ip
          ├─ whiteurl 规则和请求类型判断
          └─ user_agent → header → referer → cc → file_upload → url
             → url_args → cookie → post（受白名单跳过项和 bodyless 配置影响）
```

IP 白名单优先于组合规则，因此白名单 IP 不会被组合规则检测。组合规则先于传统阻断流程，因此可先记录、打分或拦截；若组合规则没有终止请求，传统流程仍会继续。传统流程的结果来自同一请求的检测器缓存，不会重复执行已经运行过的扫描。

## 2. L1：基础检测器

检测器在 `access.lua` 注册。表达式中的叶子字符串必须使用这些名称：

| 名称 | 检查内容 | 相关开关/说明 |
|---|---|---|
| `url` | URL 路径规则 | `url_check` |
| `url_args` | 查询参数规则 | `url_args_check` |
| `post` | 表单参数或请求体规则 | `post_check`；GET、HEAD、OPTIONS 默认跳过 |
| `header` | 请求头规则 | `header_check` |
| `cookie` | Cookie 规则 | `cookie_check` |
| `user_agent` | User-Agent 规则 | `user_agent_check`；UA 白名单可跳过此项 |
| `referer` | Referer 规则 | `referer_check` |
| `file_upload` | multipart 上传文件名/扩展名规则 | `file_upload_check`；bodyless 方法默认跳过 |
| `cc` | CC 限速检测 | `cc_check` |
| `black_ip` | 静态黑名单 IP | `black_ip_check` |
| `dynamic_black_ip` | 动态封禁 IP | 由动态封禁状态判断 |

检测器返回事实对象（通常含 `rule`，可选 `detail`、`tag`），或返回假值表示未命中。结果存入 `ngx.ctx._waf_facts`，一个请求中同一检测器最多执行一次。组合表达式使用三态结果：命中、未命中、未知。检测器异常会写错误日志并记为未知；传统检测流程仍把未知视作未命中以保持旧接口行为。

检测器本身沿用传统配置开关和各自规则文件，所以组合表达式引用一个被关闭或按请求类型跳过的检查项时，会得到未命中。为避免跳过或检测错误被取反成命中，规则校验禁止 `NOT` 子树包含任何 L1 检测器；`NOT` 仍可用于内联请求条件。表达式求值对 `AND`、`OR` 和 `AT_LEAST` 使用短路逻辑；尚未被求值到的检测器不会运行。

## 3. L2：组合规则与表达式

### 文件格式和加载

`combo.jsonl` 使用 JSON Lines 格式：每个非注释行是一条 JSON 规则，空行和以 `#` 开头的行由规则文件读取层忽略。域名配置存在 `rule_dir` 时，先从域名规则目录读取 `combo.jsonl`；该文件不存在时回退到全局 `config_rule_dir`。热加载由 `lib.lua` 的 worker 级规则缓存负责：最多每 10 秒检查文件版本，文件变更后重新读入；无需重载 Nginx。

规则读取后，`engine.lua` 按行解码并编译有效规则。规则必须有非空字符串 `id` 和 `if` 表达式；`enabled: false` 会跳过。加载时校验检测器名、内联条件名、操作符、关键参数类型及 `AT_LEAST` 的整数范围；内联 `re` 条件会预编译正则，无效 JSON、无效表达式、无效正则或未知 action 会记录错误并忽略该条规则。表达式嵌套深度上限为 16。

### 规则对象

```json
{"id":"scanner-on-api","if":["AND","user_agent",{"cond":"uri","op":"prefix","value":"/api/"}],"action":"LOG"}
```

字段：

| 字段 | 含义 |
|---|---|
| `id` | 规则标识；写入组合规则日志标签 |
| `if` | 必填表达式 |
| `action` | `BLOCK`、`LOG`、`ALERT`、`SCORE`、`CHALLENGE`；缺省为 `BLOCK` |
| `score` | `SCORE` 的加分值；缺省为 10。`SCORE` 必须为正数，否则整条规则被忽略并记录错误；非 `SCORE` 动作不校验正负 |
| `enabled` | 明确设为 `false` 时禁用 |

规则按文件顺序执行。`LOG`、`ALERT`、未达到阈值的 `SCORE` 不会停止后续组合规则；`BLOCK`、`CHALLENGE` 或达到分数阈值且 WAF 开启时会终止请求。一个请求中的分数保存在 `ngx.ctx._waf_score`，不会跨请求累计。

### 表达式

```json
"url"
["AND", "url_args", {"cond":"method","op":"eq","value":"POST"}]
["OR", "url", "header"]
["NOT", {"cond":"ip","op":"re","value":"^10\\."}]
["AT_LEAST", 2, "url", "url_args", "post", "header"]
```

- 字符串叶子：调用同名 L1 检测器。
- `AND`：所有子表达式为真。
- `OR`：至少一个子表达式为真。
- `NOT`：唯一内联条件取反；不能包含 L1 检测器。
- `AT_LEAST`：从第二个参数读取数量 `n`，后续子表达式中至少 `n` 个为真。

运算符名称区分大小写。`AND`、`OR`、`NOT` 和 `AT_LEAST` 会传播未知状态：例如未知条件不会被 `NOT` 直接变成真。编译阶段校验运算符、参数数量、检测器和内联条件名称、操作符及参数类型。

### 大小写

- **匹配内容默认不区分大小写**：传统 `.rule` 检测统一使用 `joi` 标志；内置 `combo.jsonl` 规则的 URI/body 正则均带 `(?i)` 或 `(?is)`。
- **内联条件默认不区分大小写**：`re` 默认 `joi`，`contains`/`prefix` 默认忽略大小写，`eq` 除 `method`/`protocol` 外也默认忽略大小写。
- **显式关闭**：`re` 用 `"flags":"jo"`（或任意不含 `i` 的 flags）或 `"case_sensitive":true`；`contains`/`prefix`/`eq` 用 `"icase":false`。
- **语法名区分**：检测器名、`AND`/`OR`/`NOT`/`AT_LEAST`、`cond`/`op` 字段名必须按文档大小写书写，写错会导致规则被忽略。
- `action` 不区分大小写（内部统一转大写）；`config.lua` 中的 `"on"`/`"off"` 配置值区分大小写，必须小写。

### 内联请求条件

内联条件读取请求字段，不调用 L1 规则扫描器。字段名通过 `cond` 指定：

| `cond` | 请求数据 |
|---|---|
| `uri` | `ngx.var.uri`，路径部分 |
| `args` | `ngx.var.args`，查询字符串 |
| `method` | 请求方法 |
| `protocol` | `ngx.var.server_protocol` |
| `header` | 请求头拼接成的 `名称: 值` 文本 |
| `cookie` | Cookie 请求头 |
| `body` | 请求体 |
| `ip` | `get_client_ip()` 返回的客户端 IP |
| `header_count` | 请求头数量 |
| `content_type` | Content-Type |
| `content_length` | Content-Length |
| `transfer_encoding` | Transfer-Encoding |

默认操作符为 `re`。普通字段支持：

| `op` | 语义 |
|---|---|
| `re` | `ngx.re.find` 正则搜索；**默认忽略大小写**（默认 flags `joi`）。`flags` 显式覆盖默认值，或 `case_sensitive: true` 关闭忽略大小写 |
| `eq` | 值相等比较；`method`/`protocol` 默认区分大小写，其他字段默认忽略大小写。可用 `icase` 显式覆盖 |
| `contains` | 字面子串搜索；**默认忽略大小写**，`icase: false` 关闭 |
| `prefix` | 字面前缀比较；**默认忽略大小写**，`icase: false` 关闭 |
| `exists` | 字段值非 `nil` 即为真 |

`header_count` 专用 `gte`、`lte`、`eq` 比较数量，未显式支持上表普通字段操作符。`exists` 对空字符串也返回真，只在字段为 `nil` 时返回假。

请求体读取在引擎内缓存到 `ngx.ctx._waf_body`，最多保存/扫描前 2 MiB；更大的 body 会标记为不完整。该上限由引擎固定为 2 MiB，不随 `config_post_body_scan_limit` 变化。对不完整 body，`re` 和 `eq` 得到未知；`contains` 在已扫描部分找到匹配时可判真，否则为未知；`prefix` 可在已读前缀足够时准确判断，否则为未知。读取失败也得到未知。请求头读取数量根据规则预扫描：至少读取 256 项；`header_count` 可提高上限，但最多 4096 项。达到读取上限时计数视作下界：`gte` 可在下界已满足时判真，`lte`/`eq` 在下界足以排除时判假，否则为未知。包含 `header` 条件时才构造拼接后的头文本；头列表被截断时 `re` 得到未知。

组合规则命中状态为未知时，`BLOCK` 和 `CHALLENGE` 采取 fail-closed：记录 `Combo_INDETERMINATE` 并使用统一拦截输出。`LOG`、`ALERT`、`SCORE` 仅记录该状态，不把未知当作命中（`SCORE` 不加分）。因此，阻断规则中的请求体条件遇到超过 2 MiB 的 body（包括正常的大文件上传）或读取失败时，会按设计拦截该请求。

## 4. L3：动作、日志和拦截

| 动作 | 当前行为 |
|---|---|
| `BLOCK` | 写 `Combo_BLOCK` 日志；WAF 开启时调用统一 `waf_output()` 并终止请求 |
| `LOG` | 写 `Combo_LOG` 日志，继续处理 |
| `ALERT` | 写 `Combo_ALERT` 日志，继续处理 |
| `SCORE` | 累计分值并写 `Combo_SCORE` 日志；达到阈值时再写 `Combo_SCORE_BLOCK`，WAF 开启则输出拦截响应 |
| `CHALLENGE` | 写 `Combo_CHALLENGE` 日志，复用 `waf_output()` 并终止请求 |

`CHALLENGE` 目前没有独立的人机验证或挑战流程，它和 `BLOCK` 使用相同的 HTML/重定向输出配置，仅日志标签不同。输出方式由全局或域名级 `waf_output`、`waf_redirect_url` 决定。

分数阈值配置为 `config_score_block_threshold`，默认 0：

| 取值 | 行为 |
|---|---|
| `0` | 只累计并写 `Combo_SCORE` 日志，不因 SCORE 拦截 |
| `1` | **开启拦截**：任意一次 `SCORE` 命中（累计分值 ≥ 1）即拦截。因为 `score` 默认 10，实际效果等价于“SCORE 开关” |
| `>1` | 同一请求内累计分值达到该值才拦截，可按业务容忍度设置（如 20/30） |

域名级可通过 `domain.json` 的 `score_block_threshold` 覆盖；组合规则文件也可放在域名 `rule_dir` 的 `combo.jsonl` 中独立配置。

大于 0 时建议配合更精确的条件，否则单条 `SCORE` 规则误报就会直接 403。域名级可通过 `domain.json` 的 `score_block_threshold` 覆盖。动作处理仍检查 WAF 开关；不过请求主流程在进入组合规则前已检查 WAF 总开关。

组合日志标签是动作名，规则 `id` 作为日志中的 rule 标识。L1 事实仅用于组合规则命中判断；传统检测流程的日志标签和直接 403/统一输出行为仍按原有逻辑处理。

## 5. 当前规则与编写示例

当前 `rule-config/combo.jsonl` 包含五条启用的 `BLOCK` 规则，均使用内联 URI、协议、请求头计数或请求体条件；这些规则不调用 L1 检测器。其后是被注释的组合规则示例。

仅观测 POST 请求中命中 `post` 检测器的请求：

```json
{"id":"observe-post","if":["AND","post",{"cond":"method","op":"eq","value":"POST"}],"action":"LOG"}
```

两个检测器都命中才记 30 分：

```json
{"id":"sqli-plus-rce","if":["AND","url_args","post"],"action":"SCORE","score":30}
```

建议将便宜的请求字段条件放在表达式前部，以便短路，避免不必要的检测器执行或请求体读取。修改 JSONL 时保留每条规则为单行 JSON，先用 `LOG` 观察命中日志，再按需要改为阻断动作。

## 6. 实现边界

- L1 缓存保证每请求最多执行一次检测器，不代表全局规则文件或匹配结果只读取一次；规则文件/匹配缓存由 `lib.lua` 的 worker 级缓存负责。
- 组合规则入口位于传统检测之前。它会受请求级 WAF 总开关和 IP 白名单顺序影响，但不会因为 `whiteurl.rule` 而自动跳过；whiteurl 的跳过项只在后续传统检测流程处理。
- 检测器异常被 `pcall` 捕获并标记为未知；在 `BLOCK`/`CHALLENGE` 规则中按未知状态拦截。表达式求值异常也会记录错误，并按对应动作的未知状态策略处理。
- `body` 内联条件使用引擎自身的 2 MiB 扫描上限；它与 `post` 检测器的表单解析、文件扫描及超限策略不是同一实现。
- 域名级 `rule_dir` 的单个规则文件优先于全局对应文件；若域名目录存在 `combo.jsonl`，整份组合规则表来自该文件，不会与全局 JSONL 合并。
